# Confirmed words → next transcription → review → undo

## What changed

The actual deployed component was the Cloudflare speech gateway, with a static
glossary but no confirmed learning store. This increment adds additive SQLite
tables in its existing Durable Object, token-label-scoped authenticated APIs and
a mobile `/learn` page. Confirmation records preserve the recognised spelling,
confirmed spelling, reading, note and timestamp. Review judgements append with
timestamps; undo retains provenance while disabling future hint/review use.
Every new speech request loads current hints; existing raw transcripts and audio
are not replaced. No other provider or authentication boundaries were changed.

The optional Python is an existing Playwright interpreter, not a new dependency;
it uses the shared `agents-md/tools/browser_session.py` with a fresh, task-owned
headless context and automatic cleanup. The E2E test runs a local mock Deepgram,
real workerd/SQLite/R2 simulation and synthetic credentials. It restarts the
runtime twice, preserves confirmation/review/undo across restarts, checks
multilingual hint forwarding on all three routes, isolates other/chat labels,
exercises an upstream 503 and WebSocket 1011/reconnect, verifies raw messages are
unchanged, and checks idempotent save/review/undo retries.

The mobile check (390 × 844) confirms that consent is required, simulates a save
which commits but loses its response, retries without duplicating the card,
reveals reading/meaning, reviews, reloads/reconnects, and undoes. Inputs are locked
while requests are pending so delayed responses cannot erase newer edits. No
horizontal overflow or uncaught JavaScript errors were observed.

Phone demo: `/learn?demo=1` → **Fill a synthetic example** → check confirmation →
**Confirm and remember** → inspect next-request hints → reveal → **Known** →
reload → **Undo confirmation** → reload → inspect history. Demo persistence is
explicitly browser-local; production SQLite persistence is proven separately by
the actual local runtime test, not claimed from the demo.

## Review and evidence

- 10/10 unit tests, TypeScript check, local E2E + rendered mobile check and
  Wrangler dry-run passed on 9 Nov 2026.
- Independent focused code review found one P2: editable inputs could be erased
  by a late successful response. Fixed by locking inputs during pending requests;
  the lost-response browser regression asserts this lock.
- Deepgram primary documentation: https://developers.deepgram.com/docs/keyterm
  (retrieved 9 Nov 2026). Supports multilingual Nova-3 hints, a small focused list,
  500-token cap and `redact_usage=true` for sensitive keyterms. The latter is now
  enforced; it is not an audio-retention guarantee.
- Alternatives: automatic transcript replacement was rejected because guessed
  names must not become truth. Mid-stream `Configure` is documented but deferred
  to avoid changing in-flight streams. A full FSRS/Firestore redesign was deferred
  in favour of this working gateway's smallest persistent loop.

## Limits / next bounded increment

No claim of real-world WER improvement: no real/private audio or paid Deepgram
request was used. Confirmed terms are hints, not guaranteed corrections. The
FastAPI/Firestore path and existing open streams do not automatically adopt this
loop. Labels are app-sharing scopes, not individual identity. Undo is not deletion;
provenance and review history are retained. No full transcript excerpts are saved
with corrections. Personal hint limits are conservative byte caps, not a provider
tokenizer; excessive client-supplied hints can still exceed Deepgram's token cap.
Review is a simple explicit judgement log, not FSRS or inferred proficiency.

Next: add a bounded synthetic EN/JA recognition evaluation with an approved audio
fixture/budget before claiming accuracy gains; then decide whether to bridge
confirmed terms into Firestore encounter cards or add explicit hint usage receipts.
No scheduler, background recording or new collection was created.
